# 设计：计划中的人工步骤（人机交接）

## Context

「回合边界」这套状态机把三件事统一成「收尾工具结束本轮 → session 记状态 → 推结构化卡片 →
用户回应经下一次 `chat.send`」：计划确认（`planId`）、澄清提问（`questionId`）、进度交接（`finish_turn`）。
**"某一步得由用户在页面上手做"是第四件事，但一直没有自己的表达方式**：

- 计划步骤只有 `pending` / `done`，表达不了"控制权在用户手里"；
- `chat.send` 没有相应的意图位（`ask_user` 是"问一个信息"，语义与"请你去操作"不同）；
- 进度由模型自报 ⇒ 服务端无法阻止"模型自己把人工步骤标成 done 然后继续"。

而页面的能力边界是**运行期事实**：`manifest.exposes` 与运行时上报的 `page.exposed` 才说明"这一步能不能用
`call_page_method` 做掉"，同一个"保存"按钮在不同页面 / 不同版本上可能一侧可调用、一侧不可调用。

## Goals / Non-Goals

**Goals**

1. agent 做不了的一步能被**明确交接**给用户：计划卡上该步变成"轮到你"，带**操作指引**（在哪、点什么、做到什么算完成）。
2. 交接后**只有用户能推进**：用户点「我已完成，下一步」（`chat.send.stepDoneId`）才把该步标 `done` 并起下一轮。
3. 后续步骤校验发现没做成 / 做错时，能**指到那一步**给提示（`issue`），用户改完再点「我已重做，下一步」。
4. 判定权在执行期的 agent，判据是**可查的事实**（页面能力清单 / 调用结果），不是感觉。
5. 不打扰"agent 自己能做完"的那部分：没被交接的步骤照旧自动推进，不新增任何点击。

**Non-Goals**

- 不做"逐步审批"（每一步都要用户点确认才继续）—— 由用户在验收时明确排除。
- 不在 `propose_plan` / `revise_plan` 时预先声明步骤归属（见 D4）。
- 不做宿主页面上的视觉引导（高亮目标控件 / 浮层指引）—— 那是另一档能力（需要 runtime 侧宿主 DOM 指引 API），
  本次只到"面板内提示 + 指引文本 + 必要时先 render 到目标页"。
- 不持久化等待态（会话 = 连接，刷新/重连即新会话，与既有语义一致）。

## Decisions

### D1 判据写进 prompt，但"只能由用户推进"是**服务端不变量**

**决定**：prompt 规则 16 给出判据 —— ① 动作能在「当前页可用方法」清单里找到 → 自己做；
② 写后端的动作 / 清单里没有对应方法 → `handoff_step`；③ 需要人本身才能完成的（扫码、验证码）→ `handoff_step`；
④ `call_page_method` 返回权限不足 / 校验失败 → 不要反复试，交接给用户。
同时 `applyPlanProgress` 里加硬约束：`waiting-user` 的步骤**只认** `chat.send.stepDoneId`。

**为什么**：只靠 prompt 会有两个必然失灵的场景 —— 模型"觉得用户已经做完了"（`finish_turn({ done: ['step-3'] })`）
和模型"懒得交接、自己硬试"。前者用不变量彻底堵住（进度口径在服务端）；后者 prompt + 失败信号（判据④）能覆盖，
且真有漏网也不致命：步骤还在计划里，用户能在卡片上看到它没被标完成。

**替代方案**：把人工步骤做成"计划批准前必须声明"（`propose_plan` 带 `owner`）—— 与 D4 同因被否。

### D2 一个工具 `handoff_step` 同时表达"交接"与"校验失败要求重做"

**决定**：`handoff_step({ stepId, instruction, issue? })`：不带 `issue` = 正常交接；带 `issue` = 上一次没做对，请重做。
两种情况都把该步留在（或退回）`waiting-user`（带 `issue` 时额外显示原因与期望）。

**为什么**：两者的服务端动作**完全一样**（把控制权交给用户 + 目标是这一步），差别只在文案与是否携带原因；
拆成两个工具只会让模型多一个选错的机会，还多一条 `TurnEndToolName`。用一个 `issue?` 字段表达"为什么又要你做一次"最小。

**实测修正（真机验收发现的坑）**：用户点过「我已完成」后服务端已经把该步标成 `done`，
而校验发现"没做成"恰恰发生在这之后 —— 最初的校验把"`done` 的步骤不许交接"一刀切，
于是**带 `issue` 的交接也被拒**，R3 在真机上根本走不到（模型只好退回 `finish_turn` + 一段文本，
计划里留下一条"已完成"的假记录）。现在的规则是：`done` + **不带** `issue` → 拒绝（没东西可交接）；
`done` + **带** `issue` → **允许**，把它退回 `waiting-user` 让用户重做。这也是"假记录"能被抹掉的唯一路径。

**替代方案**：`report_step_issue` 单独一个工具（语义更纯），已弃（见上）。

### D3 "至多一个步骤在等你"是不变量，等待态复用 run status `waiting-user`

**决定**：`applyHandoff` 把目标步置 `waiting-user` 的同时，把**其它**仍在 `waiting-user` 的步骤收回 `pending`；
`resolveRunStatus` 把 `handoff_step` 映射成已有的 `waiting-user`（与 `ask_user` 同一落点）。

**为什么**：UI 的动作条只打算有一个主按钮、prompt 里也只有"一个待办"——"同时等用户做两件事"会让两边都要支持多选，
本轮不需要。run status 复用则是因为语义本就是"上一轮停在等用户决策"（`ask_user` 与人工步骤都是"等你"），
靠 `chat.done.endedBy` 与卡片（有无计划卡 / 该步状态）区分即可，不必新增状态。

### D4 `owner` 只由运行期交接写入（计划期不预告）

**决定**：`propose_plan` / `revise_plan` 的入参**不加** `owner`；`PlanStep.owner` / `instructions` / `issue` 只由 `handoff_step` 写。

**为什么**（用户口径："交给 agent 判断，页面有些功能需要用户手点，有些可以直接执行下去"）：
某一步是否需要用户手做取决于**执行到那一步时页面实际能给什么能力**；计划期预告会与运行期事实打架，
而"计划说 agent 做、结果要用户做"的错位对用户的伤害大于预告带来的收益。计划卡上因此不出现"预计需要你操作"。

### D5 客户端只跟随服务端 `steps`（不本地推断人工步骤）

**决定**：`turnState` 不在本地把步骤改成 `waiting-user`/`done`，只维护两个**本地瞬时态**：
`completingStepId`（点了按钮、等本轮结束）与用 `handoffStep(card)` 从服务端 `steps` 派生的"当前等待中的一步"。
用户点完按钮后该步的 `done` 由服务端权威下发（`chat.plan`）。

**为什么**：`waiting-user` 的进出有两个来源（`handoff_step` 交接、`chat.send.stepDoneId` 推进），
且 `handoff_step` 可能把它收回 `pending` —— 本地推断必然漂移（这与计划修订"只跟随 `status`"的教训相同）。

**因此服务端必须在推进成功后立刻回推一张卡片**（在 gateway 的 `resolveTurnEndInput` 里，与 `completeUserStep`
同一处）：那一轮很可能一张卡片都不推（模型校验后直接继续下一步；`finish_turn` 只推文本）。
不推的话客户端只能等下一张卡片，界面会一直显示"轮到你操作"，用户以为白点了 ——
"只跟随服务端"这条规矩要求服务端在每次状态变化后都把状态说出来。

### D6 `waiting-user` 的步骤在 prompt 里必须与其它步骤写法不同

**决定**：`[当前计划]` 段落三态标记（`[x]` 完成 / `[~]` 已交给用户 / `[ ]` 待做），并给 `waiting-user`
的步骤附上"等他完成后点「我已完成，下一步」（这一步不要你自己做）"与给他的指引；进度行也不再把它列进
"`finish_turn` 的 `done` 请填这些步骤 id"。

**为什么**：这两处是模型最容易走偏的地方 —— 把人工步骤当自己的步骤接着做、或顺手填进 `done`
（后者已被服务端不变量拦住，但 prompt 写得含糊会让模型反复尝试、白烧步数）。

## Risks / Trade-offs

- **模型不交接、硬试**：prompt 判据 + 失败信号兜底；真漏网时步骤仍在计划里（用户可见未完成），
  不会出现"用户不知道要自己做"的静默失败。
- **用户点了「我已完成」但其实没做完**：下一轮模型校验（规则 17）→ 带 `issue` 让它重做（幂等，不推进进度）。
  代价是多一轮模型调用，这是"必须校验"的必然成本。
- **`waiting-user` 与 `ask_user` 共用 run status**：日志与 UI 需要靠 `endedBy` + 卡片区分；文档写清两种"等你"。
- **刷新 / 重连丢等待态**：与整个会话模型一致（连接作用域），文档注明。
- **修订与等待的交互**：`revise_plan` 命中 `waiting-user` 的步骤时保留其 `owner` / `instructions` / `issue`（`reopen: true` 才回 `pending` 并清 `issue`）；步骤被删除则等待自然消失。
